## Portal Settings evidence chain

The deployed source proves only specific independent systems: `portal-settings` is a seeded module label with a frontend `/settings` mapping; expense settings fields are validated and stored per company; company module visibility is stored per company and consumed by `my-company-modules`. It does **not** prove that any of these fields appeared on an expanded Portal Settings screen. The V1 frontend Git sidebar suggests the name was a navigation group, but that is **V1-GIT EVIDENCE**, not proof of the deployed screen. Its `/fbr` Invoice Data link conflicts with the deployed seeder's `/settings` mapping, so neither path establishes the deployed UI by itself.

## PDF evidence boundary

The directly inspected local `Zavsync Portal - Payment Management System.pdf` defines the visible one-page layout/content of a future dynamic invoice view/print. It contains seller/buyer identity, invoice and FBR numbers, issue date/status, the item table, subtotals, FBR POS/QR area, computer-generated declaration and branded footer. It does **not** establish that the QR is verifiable, that the PDF was generated by a particular backend route, or that long invoices paginate correctly. Its example seller, buyer, identifiers, number, QR and amounts are not defaults. V2 must render only data preserved for the particular invoice, and use the certified V2 backend for calculations, status, provider evidence and credit authority.
